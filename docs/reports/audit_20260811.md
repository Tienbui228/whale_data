## A — ROOT CAUSE: A3 SLOPE BOUNDARY FLIP

**Claim:** identify exact mechanism causing 15+ chain state discrepancy between backup (59 open) and corrupted cron run (44 open).

### Evidence

**Probe:** `_probe_a_ff_signals_20260811.py` — fetches VPS freshwatch 2026-07 + 2026-08, computes A1/A3 per day for FFUSDT.

**Key measurement (2026-08-01):**
```
gLSR(07-27) = 0.6093   [5th-present-prior row, positional]
gLSR(08-01) = 0.7001
slope5       = 0.7001 / 0.6093 = 1.14902
threshold    = 1.15
margin       = +0.00098   ← 0.098% from flip
```

**A3 boundary table (slope near 1.15±0.05):**
```
2026-07-30  slope=1.14844  A3=PASS  margin=+0.00156
2026-08-01  slope=1.14902  A3=PASS  margin=+0.00098  ← critical
```

**Gap effect:** Dates 2026-07-24, 2026-07-25, 2026-07-26 are ABSENT from freshwatch (system-wide gap). `gom_scan.py:276` uses **positional** indexing `days[i-5]` — not calendar days. The 5th-prior-present-row at 08-01 is 07-27, not 07-27 by calendar coincidence but because the gap shifts which physical row is i-5.

**Full-rebuild vs incremental divergence mechanism:**  
The freshwatch CSVs are exported at 01:20 UTC. The cron was scheduled 01:25 UTC (5 min later). If gLSR for any in-window date was re-stamped (even epsilon) between the export used for the backup and the export used by the cron's full-rebuild, the rolling buffer fills differently → slope5 crosses 1.15 → A3=FAIL → chain never opens.

**Code reference:** `scripts/gom_scan.py:276–277`
```python
g0 = days[i-5].get("lsr_global", float("nan"))   # positional, not calendar
```

### Finding

**Severity: P1**  
A3 has zero hysteresis. A 0.1% movement in gLSR (one token, one day) silently kills a chain. The full-rebuild used a fresher CSV snapshot than the backup — gLSR values updated between export runs are enough to flip A3.

**Proposed fix (post-gate 15/08):**  
Add hysteresis band to A3: threshold `1.13` for open (conservative), `1.15` for continuation — or min-hold: once chain is open, A3 violation triggers cooldown rather than immediate close. Requires operator sign-off on threshold change (thresholds.yaml gated).

**L-28 conclusion:** No hysteresis exists in current A3 implementation. The P0 incident was a deterministic boundary flip caused by (a) positional gap sensitivity and (b) CSV timestamp delta between backup and cron run. The fix was correct: incremental §8.2 prevents re-evaluating already-opened chains.

## F — GOM_STATE.JSON POST-WRITE GUARD MISSING

**Claim:** verify gom_state.json write path has post-write validator.

### Evidence

**Code reference:** `scripts/gom_scan.py:768`
```python
def save_state(state, path):
    with open(path, "w", encoding="utf-8") as f:
        json.dump(state, f, indent=2, ensure_ascii=False, default=str)
```

No `validate_gom_state()` call after write. The guard V2 (`validate_written_pack`) covers CASE xlsx, not gom_state.json.

Compare: `build_case.py:863` calls `validate_written_pack(XLSX)` post-write ✓  
Compare: `scripts/case_daily.py:446` calls `validate_written_pack(xlsx_path)` post-write ✓  
**Gap:** gom_state.json has no equivalent.

### Finding

**Severity: P1**  
If save_state() writes a partially corrupt JSON (disk full, encoding error, truncated write), the next cron load `json.load()` will raise → cron fails. But a schema-invalid JSON that loads correctly (e.g., wrong types, missing required keys) would silently propagate.

**Fix:** After `save_state()`, call a `validate_gom_state(state)` that checks: all tokens have required keys, chain_open is bool, dates are string or None. Raise on violation. Wire into `gom_scan.py` immediately after save call.
